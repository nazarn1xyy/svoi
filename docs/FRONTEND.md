# FRONTEND.md — тимлід + фронтенд бота

Файл для твоєї сесії нейромережі. Ти виконуєш дві ролі: **тимлід** (скелет, CI/CD, контракти, спільні файли, рев'ю) і **фронтенд** (бот: сценарії, клавіатури, картки, тексти, воркер сповіщень, адмін-бот).

Ядро: `docs/tech.md`, поточна версія **v1**.

## 0. Прочитай першим

- `docs/tech.md` — джерело істини. Підкоряйся йому дослівно. У Claude Code ядро підтягується через `CLAUDE.md` автоматично; у будь-якій іншій сесії приклади `tech.md` до цього файлу.
- Перед задачею звір версію ядра в заголовку `tech.md` з версією, на яку посилається задача. Ядро новіше — перечитай changelog.
- Контракти (схема БД, моделі API, топіки черги, примітиви UI, константи) не вигадуються. У ролі фронтенду бракує контракту — `CONTRACT GAP` (розділ 3), навіть якщо ти ж і тимлід: спочатку змінюєш ядро окремим PR `contracts`, потім фічу. Це тримає бекенд у синхроні.
- Одна задача за раз. Сфокусований дифф, а не весь бот одразу.
- Слайс повторює структуру еталонного слайса S1: `apps/bot/svoi_bot/features/start` і `features/onboarding`. Не вигадуй свою розкладку.

## 3. CONTRACT GAP

### Коли ти фронтенд

Бракує поля, ендпоінта, примітива, енуму або тексту-ключа, який повертає API → СТОП. Видай блок з розділу 16 `tech.md`, відкрий issue `contract-change`, продовжуй фічу на локальній заглушці всередині `features/<slice>/`. Код з вигаданим типом не пиши. Потім виконай роль тимліда (нижче).

### Коли ти тимлід (блок прийшов від бекендера або від тебе)

1. Оціни: чи потрібне поле взагалі, чи вирішується наявним контрактом.
2. Окремий PR `lead/SVO-<n>-contract-<slug>`:
   - зміна в `docs/tech.md` (append-only), бамп версії, рядок у changelog;
   - `svoi_contracts`: модель/енум/константа, `CORE_VERSION += 1`;
   - якщо зачіпає схему — модель у `db/models.py` + `alembic revision --autogenerate`, перевір міграцію руками;
   - якщо зачіпає фікстури — перегенеруй сид і `fixtures/`;
   - `FakeApiClient` — новий метод або поле.
3. Рев'ю бекендера, мердж, закрий issue посиланням на PR.
4. Великі рішення (нова сутність, зміна нарізки) — ADR у `docs/adr/NNNN-<slug>.md`. Якщо встановлено skill `engineering:architecture` — використовуй його для ADR.

| Job | Кроки |
| --- | --- |
| `lint` | `uv run ruff check .`, `uv run ruff format --check .` |

| `bot` | сервіс `redis:7`; `pytest apps/bot` (з `FakeApiClient`, включно з `test_all_clarification_keys_translated` і перевіркою, що всі ключі uk є в `.po`) |
| `build` | `docker build` для `apps/api` і `apps/bot` |

### Деплой — `.github/workflows/deploy.yml`

- push у `main` → збірка образів, push у GHCR з тегом `sha` → SSH на тестовий VPS → `docker compose pull` → `docker compose run --rm api alembic upgrade head` → `docker compose up -d` → smoke: `GET /health` через внутрішню мережу і `getWebhookInfo` без помилок.
- тег `v*` → той самий сценарій на прод через GitHub Environment `production` з ручним підтвердженням.
- Міграції застосовуються тільки в кроці деплою, ніколи на старті контейнера.

## 7. Long-lead — запусти в перший день

Long-lead блокує реальну інтеграцію, не розробку: усе розробляється проти фейків з першого дня.

- BotFather: 4 боти — основний тест, основний прод, адмін тест, адмін прод. Опис, аватар, команди.
- Два VPS (тест, прод), домен, DNS-записи під webhook.
- GeoNames: дамп міст України з альтернативними назвами uk/ru для таблиці `cities`.
- Довідник закладів освіти: зібрати з відкритих даних (наприклад, реєстр закладів освіти ЄДЕБО); перевірити ліцензію і формат. До готовності — 3 міста вручну в сиді.
- NSFW-модель: вибрати open-source модель, запакувати в контейнер з HTTP-ендпоінтом.
- Тексти правил і політики конфіденційності (посилання на екрані згоди).
- Sentry-проєкт, Linear-воркспейс, GitHub-організація, GHCR.
- Юзернейм підтримки для `/help`.

## 9. Фронтенд-слайси

Кожна задача — один вертикальний слайс бота, один PR. Код фічі: `features/<slice>/{router,states,handlers,views}.py`. Тексти — ключі в `locales/uk/LC_MESSAGES/messages.po` (+ ru, en до релізу стадії). Нижче тексти наведено мовою uk.

Загальні правила для всіх слайсів:

- Кроки з кнопками редагують одне повідомлення через `ui.screen.Screen`; текстове введення користувача — нове повідомлення бота.
- Кожен крок онбордингу починається з `step_header(step)`: «Крок N з 10». Нумерація: age 1, name 2, gender 3, city 4, goals 5, interests 6, institution 7, height 8, prompts 9, media 10; `clarify` і `preview` без номера.
- Онбординг відновлюється з `UserState.onboarding_step` при будь-якому повідомленні, поки `status = onboarding`. Реєстр екранів кроків: `features/onboarding/registry.py`, `STEP_SCREENS: dict[OnboardingStep, StepScreen]`, режими `onboarding` і `edit`.
- Будь-яка `ApiException` → `ui.errors.render_api_error`; стан FSM не губиться, користувач лишається на тому самому кроці.
- Таймаут API → «Щось пішло не так. Спробуй ще раз за хвилину.» і та сама клавіатура.

### S1-FE — старт, мова, згода, вік, ім'я, стать (еталон, MVP)

**Ціль.** Новий користувач проходить перші кроки онбордингу; той, хто кинув, продовжує з того самого кроку.

**Файли.** `features/start/`, `features/onboarding/` (`registry.py`, `states.py: OnboardingSG`).

**Контракти.** `POST /users/start`, `GET /users/me`, `PUT /users/me/lang`, `POST /users/me/consent`, `PUT /profile/age`, `PUT /profile/name`, `PUT /profile/gender`; `UserState`, `StartIn`, `ErrorCode.age_too_young|age_locked|content_blocked|banned`.

**Примітиви.** `inline_choice`, `Screen`, `step_header`, `render_api_error`.

**Екрани.**

1. `/start [r_<code>]` → `start(StartIn)`: `has_tg_profile_photo` через `get_user_profile_photos(limit=1)`, `referral_code` з deep-link `r_<code>`. Далі екран за `onboarding_step`.
2. Мова: «Choose your language 👇». Кнопки: `🇺🇦 Українська` `🇬🇧 English` `🇷🇺 Русский`.
3. Згода:
   > Привіт! Я допомагаю знайти людей зі спільними інтересами — друзів, компанію, напарників. Це не сайт знайомств. Заповнимо анкету за 2 хвилини?
   >
   > ❗ Бот не просить документів і особистих даних. В інтернеті люди можуть видавати себе за інших.
   >
   > Продовжуючи, ти приймаєш [правила] і [політику конфіденційності].

   Кнопки: `👌 Поїхали` `❓ Як це працює`. «Як це працює»: «1. Заповнюєш анкету: інтереси, місто, мета. 2. Дивишся анкети людей поруч зі спільними інтересами. 3. Лайкаєш. Якщо лайк взаємний — отримуєте username одне одного і пишете в особисті.» + `◀️ Назад`.
4. Вік: «Крок 1 з 10 · Скільки тобі років?» Введення числом.
   - не число → «Напиши вік цифрами, наприклад 19»;
   - `age_too_young` → «Бот доступний з 16 років. Повертайся, коли виповниться 16 🙂»;
   - `age_locked` → «Вік уже не можна змінити. Якщо помилився — напиши в підтримку: /help».
5. Ім'я: «Крок 2 з 10 · Як до тебе звертатися?» Кнопка з `first_name` з Telegram, якщо 2–20 символів, або введення свого. `content_blocked`/`validation_error` → «Ім'я — від 2 до 20 літер, без посилань і цифр».
6. Стать: «Крок 3 з 10 · Ти…» `Хлопець` `Дівчина` `Не вказувати`. Підказка: «Потрібно тільки для фільтра «з ким хочу спілкуватися», в анкеті можна приховати».
7. `banned` на будь-якому кроці → «Твою анкету заблоковано до {date}.» або «Твою анкету заблоковано назавжди.» Без клавіатури.

**Критерії приймання.**

- `/start` новим користувачем показує вибір мови; після вибору всі подальші тексти мовою вибору.
- Користувач, який закрив чат на кроці «Стать», після будь-якого повідомлення бачить екран «Стать».
- Вік 15 показує відмову; повторне введення показує `age_locked`-текст (бекенд блокує).
- Кнопка з ім'ям з Telegram не показується, якщо ім'я довше 20 символів.
- Помилка API на кроці не скидає стан: повторне введення працює.
- Реферальний код з `/start r_ABC123` передається в `StartIn.referral_code`.

**Тести.** Harness: повний прохід S1 проти `FakeApiClient`; відновлення з кожного кроку (параметризовано по `OnboardingStep` S1); `fail_next("set_age", age_too_young)` → текст відмови; `timeout_next("set_name")` → текст помилки і стан `OnboardingSG.name`; контракт: `FakeApiClient` падає, якщо бот шле `age` рядком. Property: для будь-якого `first_name` кнопка з ім'ям є тоді й лише тоді, коли довжина в `NAME_LEN`.

**Екрани.**

1. Сповіщення `bot.notify_likes`: «❤️ Ти сподобався {count} людям! Подивитися?» (множина через `ngettext`: 1 людині / 2 людям / 5 людям) + `👀 Подивитися` `⏰ Пізніше`.
2. `❤️ Мене лайкнули` / `/likes` / `👀` → `GET /likes/incoming/next` → картка (`mode=incoming`) + «💌 Повідомлення для тебе: {message}» (голос/кружок — окремим `send_voice`/`send_video_note` за `file_id`) + inline `❤️ Взаємно` `👎 Ні` `⚠️`.
3. `👎` → наступний вхідний; `NoIncoming` → «Це всі. Повертаємось до анкет?» `🔍 Дивитися анкети`.
4. Взаємність (з `RespondOut.match`, `ReactionOut.match` або з воркера):
   > 🎉 Взаємна симпатія з {name}! Пиши: @{username}

   + картка (`mode=match`) + inline-кнопка URL `💬 Написати` (`https://t.me/{username}`).
   - Айсбрейкер (1.1): `common_interest` → «Привід почати: ви обоє любите {interest} — спитай, з чого все почалось»; `same_institution` → «Привід почати: ви з одного закладу — {institution}»; `common_goal` → «Привід почати: ви обоє шукаєте {goal_label}».
   - Немає username → «У {name} немає username. Спробуй відкрити профіль:» + URL-кнопка `tg://user?id={tg_id}` + «Посилання може не відкритися через налаштування приватності».
5. `🤝 Мої контакти` / `/contacts` → список по 10: кнопка «{name}, {age} · {city}» на кожен контакт, `PageCb` для пагінації. Контакт → `💬 Написати` `🚫 Видалити контакт` `⚠️ Поскаржитися`. Порожньо → «Поки немає контактів. Взаємні симпатії з'являться тут.»
6. Воркер `bot.notify_match`: `GET /matches/{match_id}` від імені `recipient` → той самий екран взаємності.

**Воркер — обов'язково.** Перед надсиланням `SET notify:sent:{dedupe_key} NX EX 604800`; ключ є → вихід. Мережева помилка/5xx Telegram → видалити ключ і підняти виняток (ретрай arq). 403 → `bot-blocked`, без ретраю. Успіх → `notifications/{dedupe_key}/sent`. Тексти мовою з `payload.lang`.

**Критерії приймання.** Вхідні лайки показуються раніше за стрічку; відмова нічого не надсилає автору; взаємність надсилається обом рівно один раз.

**Тести.** Harness: потік вхідних з повідомленням і без; accept → взаємність; decline; контакти з пагінацією і видаленням. Воркер: **ідемпотентність** — `notify_likes` двічі з тим самим payload → один `sendMessage`; `notify_match` двічі → один; шлях помилки: Telegram 500 → ретрай, ключ знято; 403 → виклик `bot-blocked`, без ретраю; контракт: невалідний payload → лог без надсилання.

### S10-FE — скарги, блок, адмін-бот (MVP)

**Ціль.** Користувач скаржиться або блокує; модератор розбирає черги в адмін-боті.

**Файли.** `features/report/`, `admin/features/queue/`, `workers/notify_moderation.py`.

**Контракти.** `POST /reports`, `POST /blocks`, `DELETE /blocks/{id}`, `GET /admin/queue`, `GET /admin/queue/stats`, `POST /admin/actions`, `GET /admin/users/{tg_id}`; джоб `bot.notify_moderation`.

**Скарга.** `⚠️` → «Що не так з анкетою?» `Спам або реклама` `Фейк або бот` `Неприйнятні фото` `Образи` `Виглядає молодше вказаного віку` `Шахрайство` `Інше` + `🚫 Заблокувати` + `◀️ Скасувати`. «Інше» → «Опиши коротко, що не так (до 500 символів).» Після: «Дякуємо, ми перевіримо. Цю анкету ти більше не побачиш.» → наступна картка (у стрічці) або назад (у вхідних/контактах). `conflict` → «Ти вже скаржився на цю анкету.» Блок → «Заблоковано. Ви більше не побачите одне одного.»

**Адмін-бот.** `/start` (тільки `ADMIN_TG_IDS`, інші — «Доступ заборонено») → «Черги модерації» з кнопками `Скарги ({n})` `Фото ({n})` `Верифікації ({n})` `Свої теги ({n})` `Тексти ({n})`. Черга → елемент: картка (`mode=admin`, з pending-медіа), список скарг «{reason} · {date} · {text}», кнопки за типом:

- `reports`: `✅ Все гаразд` `🖼 Видалити фото` `✏️ Видалити текст` `⏳ Бан 7 днів` `⛔ Бан назавжди` `🔞 Перенести в пул 16–17`;
- `photos`: фото + `✅ Схвалити` `❌ Відхилити`;
- `verifications` (S12): кружок + «Очікуваний жест: {gesture}» + фото анкети + `✅ Схвалити` `❌ Відхилити`;
- `custom_tags`: «{title}» + `✅ Схвалити` `❌ Відхилити`;
- `texts`: текст + `✅ Все гаразд` `✏️ Видалити текст` `⏳ Бан 7 днів`.

Бан і «Видалити» питають підтвердження. Після дії — наступний елемент; черга порожня → «Черга порожня 🎉». `/user <tg_id>` → `AdminUserOut`.

**S10b — `/metrics [days]`** в адмін-боті (`GET /admin/metrics`, за замовчуванням 7 днів): «Метрики за {from}–{to}: старти {starts}, завершили анкету {onboarding_rate}%, взаємних лайків {mutual_rate}%, утримання D1 {d1}% / D7 {d7}%, скарг на 1000 показів {reports}, підтверджених скарг {confirmed}%». Тест: рендер з фейка, ділення на 0 не ламає текст.

**Сповіщення користувачу** (`bot.notify_moderation`): `media_rejected` → «Одне з твоїх фото не пройшло модерацію і видалене. Додай інше в «Моя анкета».»; `text_removed` → «Текст у твоїй анкеті видалено: він порушував правила.»; `banned` → «Твою анкету заблоковано{ до {until}}. Причина — порушення правил.»; `unbanned` → «Блокування знято. З поверненням!»; `verified` → «Готово! Твоя анкета верифікована ✅»; `verification_rejected` → «Не вдалося підтвердити верифікацію. Спробуй ще раз: /verify»; `tag_approved` → «Твій інтерес схвалено і додано до анкети.»; `tag_rejected` → «Твій інтерес не пройшов перевірку.»

**Критерії приймання.** Скарга з причиною «Інше» без тексту не надсилається; не-адмін не бачить черг; кожна дія модератора — один `POST /admin/actions`.

**Тести.** Harness: скарга кожною причиною; «Інше» з текстом; блок; адмін-бот для адміна і не-адміна; дія → наступний елемент. Воркер `notify_moderation`: ідемпотентність, 403, 500.

### S11-FE — антибот: капча і помилки контенту (MVP: помилки; 1.1: капча)

**Ціль.** Підозрілий акаунт проходить капчу; заблокований контент пояснюється зрозуміло.

**Файли.** `features/captcha/`; розширення `ui/errors.py` (тимлід).

**Контракти.** `POST /users/me/captcha`, `POST /users/me/captcha/verify`; `UserState.captcha_required`; `ErrorCode.captcha_required|content_blocked|rate_limited`; `ContentBlockReason`.

**Екрани.**

- `captcha_required` (з `UserState` або з помилки) → «Перевірка, що ти не бот: натисни на {emoji}» + 6 емодзі в сітці 3×2. Помилка → «Не вгадав, спробуй ще» і нова капча. Протухла → нова капча. Успіх → повернення туди, де був користувач.
- `content_blocked` за причиною: `link` → «Посилання заборонені.»; `mention` → «Згадки @ заборонені. Контакти відкриються після взаємної симпатії.»; `phone` → «Номери телефонів заборонені.»; `stopword` → «Текст схожий на рекламу. Перепиши його.»; `age_mismatch` → «У тексті вказано інший вік, ніж в анкеті. Виправ текст.»

**Критерії приймання.** Після капчі користувач продовжує з того самого стану FSM; користувач без `captcha_required` капчу не бачить.

**Тести.** Harness: капча правильно/неправильно/протухла; відновлення стану після капчі; кожна причина `content_blocked` → свій текст (параметризовано по енуму, тест падає при новому значенні без тексту).
